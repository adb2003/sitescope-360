# Sample data

Demo 360 panoramas, a matching floor plan, and a 360 video walkthrough — **all generated by this
repository**. Nothing here is downloaded, and no third-party or proprietary imagery is used (§37).

```
sample-data/
├── floorplans/
│   └── ground-floor-plan.png     920 × 640 px, 40 px per metre
├── panoramas/
│   ├── PANO_000.jpg … PANO_005.jpg   2048 × 1024 equirectangular
│   └── walkthrough.mp4               8 s, 10 fps, 2:1 equirectangular
└── manifest.json                 ground-truth camera positions
```

## Regenerating

```bash
python infrastructure/scripts/generate_sample_data.py

# Higher resolution (4096-wide panoramas score `good` on quality; 2048 scores `warning`)
python infrastructure/scripts/generate_sample_data.py --width 4096 --frames 12

# The whole walk, plus a video
python infrastructure/scripts/generate_sample_data.py --frames 0 --video

# Frames far enough apart that automatic mapping correctly refuses
python infrastructure/scripts/generate_sample_data.py --step-m 6
```

## Why generated rather than downloaded

Two reasons, and the second is the useful one.

**Licensing.** Public-domain 360 construction datasets are scarce and awkwardly licensed, and the
brief forbids using any proprietary vendor's imagery. Rendering our own removes the question
entirely: every pixel comes from `backend/app/processing/synthetic.py`.

**Real geometry.** The panoramas are ray-cast from *known* camera positions inside a known room,
so consecutive frames contain true parallax. The feature matcher, the essential-matrix solver and
the position estimator therefore operate on genuine multi-view geometry, and their output can be
checked against the camera path that produced it. `manifest.json` records that path:

```json
{
  "file": "panoramas/PANO_002.jpg",
  "camera_world_xz_m": [-7.5, -1.0],
  "floor_plan_px": [160.0, 260.0]
}
```

Two unrelated stock panoramas would only ever exercise the code paths, never the correctness.
This is what makes the 0.13 m accuracy figure in
[docs/VISION_PIPELINE.md](../docs/VISION_PIPELINE.md) a measurement rather than an impression.

## Using them

You do not need these files to run the platform — `python -m app.seed --demo` generates its own
imagery directly into storage. Use them to exercise the real upload path by hand:

1. Sign in, create a project, a building and a floor.
2. **Floor Plans** → upload `floorplans/ground-floor-plan.png`.
3. **Site Capture** → start a capture on that floor → upload the `PANO_*.jpg` files → process.
4. Open the **360 Viewer**, then place each frame on the plan. The `floor_plan_px` values in
   `manifest.json` are the exact pixel coordinates the camera occupied.
5. Upload the same panoramas again as a second capture session, bind them to the same points, and
   the **Compare** view has two dates to work with.

To exercise video frame extraction, upload `panoramas/walkthrough.mp4` instead and set the frame
interval on the capture session (2 s yields 4 frames from the 8-second clip).

## The scene

A 20 × 12 m room, 3.2 m floor to soffit, with four 0.7 m structural columns at (±5, ±3) and an
opening in the +X wall. Surfaces carry blocky procedural texture with formwork joints, a floor
slab grid and ceiling service runs — chosen because ORB detects **corners**, and smooth gradient
noise produces almost none.

The floor plan is rendered from the same room model, so its scale is exact rather than estimated:
a capture point dropped where the operator walked lines up with the geometry visible in the
panorama.
